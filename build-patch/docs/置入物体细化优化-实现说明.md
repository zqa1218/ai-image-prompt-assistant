# 置入物体 · 细化阶段「待定项清单」优化

> 目标：让 Gemini 把「还没定、但会影响成片」的参数主动列成可点选项，用户点两下就完成细化，而不是自己想问题、自己写长句。

- 改动对象：`prompt-wizard` v0.3.4（安装态 Electron 应用）
- 约束：安装包里**只有前端构建产物**（`dist/assets/index-*.js`，415 KB 压缩代码），没有原生工程 → 改动以**字符串级补丁**打在 bundle 上，7 处，全部带锚点断言
- 结果：补丁产物 `patch/app-patched.asar`（16,080,897 字节，与原 16,074,822 字节基本同体积），已在一份完整应用副本上**跑通真实 Gemini 3.8 Flash**

---

## 一、改之前的真实状况（先纠正一个常见误判）

细化阶段并不是「死的一块文本框」。它的组件是：

```js
function Wd({selected, notes, messages, busy, onAsk})
```

- `messages` 是一个问答线程，`onAsk` 落到 store 的 `addNote`
- `addNote` 里**真的会调模型**：`G.askDetail({...a, notes:[...a.notes, i]}, i)`，回答以 `role:'assistant'` 追加进线程
- detail 阶段的系统指令是：`回答用户的具体问题。如果用户的补充里缺了影响执行的关键信息，最多追问三个问题；否则直接给出判断与两三种可选写法。不要输出 json。`

所以现状是：**模型本来就会追问，但只有你先开口它才追问，而且返回的是散文，没法点选**。另外有两个副作用：

1. 用户的问题会被当作「补充要求」写进 `notes`（`## 用户补充要求` 里会出现一整句疑问句）；
2. 回答不会进入 `notes`，用户还得手动再写一遍决定。

## 二、设计

### 2.1 不新增阶段、不新增接口

复用已有的 `detail` 模型通道，用**一个 focus 哨兵**切换输出契约：

```js
Ru(e, 'detail', '【待定项清单】')   // 触发 strict JSON 模式
```

`gu(e)` 的 detail 分支改为：

```js
if (focus 以「【待定项清单】」开头)
   → 只输出 {"items":[{q, why, options:[{label,note}], recommended}]}
else
   → 原来的散文指令（一字未改）
```

好处：

- 固定前缀（`analysis-framework` 等资产）**一个字没动**，资产页的缓存前缀哈希不变；
- 只多一次可选的模型调用，普通问答行为完全不变。

### 2.2 抓清单不污染 notes，写答案也不再调模型

新增两个 store 动作，与 `addNote` 明确分开：

| 动作 | 行为 |
|---|---|
| `loadChecklist()` | 调 `askChecklist` → 解析 JSON → 存进新的 `questions` 状态；**不写 notes、不写 messages** |
| `answerChecklist(text)` | 把汇总结果作为一条 note + 一条 user 消息写入；**不触发模型** |

### 2.3 只在置入物体路径出现

面板由现有的 `mu(e)` 判定（`workflow.id==='refine' && taskType 含「置入物体」`），其他修图任务不受影响。

### 2.4 解析容错

`parseChecklistItems` 会：

- 从回复里截取第一个 `{` 到最后一个 `}`，容忍 ```json 围栏和前后夹的解释文字；
- 选项少于 2 条的条目直接丢弃；
- 完全解析不出时返回空数组，UI 给出「没能解析出待定项，可以重新抓取或直接写补充要求」，不报错。

### 2.5 顺手修掉 `[cite: N]` 泄漏

上一轮实跑发现角标会进最终提示词，与本应用自己的规则冲突。这次在两处各剥一层：

- 写入备注的汇总文本（`qdPanel` 里的 `strip`）
- 最终提示词输出（`Gu` 里 `?Du(n):n` 之后统一 `replace(/\[cite:[^\]]*\]/giu,'')`）

## 六、还没做到的

1. **没演练「解析失败」的真实分支**：只做了函数级退化测试，没在真实模型返回散文时走过一遍 UI。
2. **每点一次「列出待定项」就多一次模型调用**：目前是用户显式点击才触发，没有做「自动在进入细化时抓一次」。如果你想要自动，`case 'detail'` 挂一个 effect 即可，但要接受每次进细化都多一次调用。
3. **选项不可编辑**：只能在「补充要求」里另写一句覆盖，没有做「在选项上直接改字」。
4. **仍是 DOM 层面的改动**：如果官方后续更新了 bundle，这 7 处锚点会失效（补丁脚本会直接报错，不会改坏）。要长期维护，应该把 E1–E7 等价地写进真实前端工程。
5. 演示模式下 `askDetail` 返回的是一句固定文案，会走到「没能解析出待定项」的兜底——这是预期行为，但没有单独截图。
